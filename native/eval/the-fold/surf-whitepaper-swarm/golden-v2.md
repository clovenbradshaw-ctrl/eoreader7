# SURF: Active Multi-Source Search for Form and Material in eoreader7's Generation Pipeline

*A technical white paper on stage 3 of eoreader7's nine-stage generation pipeline.*

## Introduction / Summary

A generation pipeline that composes only from whatever material it was handed cannot tell the difference between "there was nothing to find" and "nothing was ever looked for" — and it will confidently produce the wrong shape as a result, because a shape it never checked is a shape it guessed. eoreader7's nine-stage pipeline (`pipeline-run.mjs`) treats this as a design commitment: stage 3, SURF, is the point at which the pipeline stops trusting its own priors about a form and starts looking for real, current, multi-source evidence of what that form actually is and what material actually exists about the ask's subject. SURF runs two independent hunts derived entirely from the prior stage's own "void" declaration — an *exemplars* hunt for instances of the named form, and a *material* hunt for sources about the ask's subject — each built from context-carrying queries rather than a bare search token, each bounded on two timescales so a slow or rate-limiting endpoint cannot stall the pipeline indefinitely, and each disclosing failure by type rather than collapsing every non-result into a silent "nothing found." Two dated, measured findings from the day SURF was built now govern its query design: a garbled or unfamiliar form-word resolves correctly only when searched with its surrounding context, never alone; and the ask's subject, if allowed into the exemplar hunt, actively degrades the signal stage 4 (SHAPE) needs to learn the form's real shape. This paper documents SURF's mechanism, the measured evidence behind its two central design rules, and its handoff to SHAPE — the stage that decides, from what SURF surfaced, whether any candidate actually satisfies the ask's void.

## Background / Problem

Ask a language model to "write a sonnet about the Cumberland River" and it will produce fourteen lines, or thirteen, or sixteen, according to whatever the model happened to internalize about sonnets during training — a shape it cannot cite, defend, or update. Ask it to write a "whiteppr" (a garbled ask this project's own testing used deliberately) and it must first guess what form is even meant before it can guess the form's shape. Either way, the pipeline is trusting a prior instead of checking the world, and a prior is exactly the thing that is silently wrong in the cases that matter most: the unusual form, the form named by an unfamiliar or misspelled word, the ask whose subject pulls a naive search toward material that has nothing to do with the form being produced.

`pipeline-run.mjs`'s own header lists its nine stages in order — PROMPT, VOID, SURF, SHAPE, HUNT, SKELETON, SK. LOOP, PATHOS, PIECE — each "proven by its own falsifier before the next was wired." SURF is stage 3, the point where the pipeline stops trusting its own priors and starts looking. Its own header states the alternative it refuses: "Not 'the file I was handed': an active search." That refusal quotes the user directive that produced it directly: "it surfs and seeks a shape of the void, extracting it from multiple sources … if we dont hunt for the shape of what would satisfy, everything breaks." The sentence names the real failure mode SURF exists to prevent: a downstream stage with nothing real to learn a form's structure from is a stage that has to invent one or say nothing, and neither is a substitute for looking.

A stage that only reads what it was handed also fails in a second, quieter way: it cannot distinguish "there was nothing to find" from "I never actually looked." Those are different findings with different consequences for what a pipeline may safely do next, and SURF's design treats the distinction as load-bearing, not cosmetic — every failure mode the web can produce is typed on the object SURF returns, never collapsed into a bare empty result.

## Solution: Two Hunts, Both From the Void's Own Words

SURF derives its queries entirely from the pipeline's own prior stage — the "void" stage 2 declared — never from external configuration. `surfQueries(spec)` reads two fields off the void spec: `spec.form.token`, the form-word the ask named (the code's own comment gives "whiteppr" as an example of a token still worth seeking "even when unresolved"), and `spec.topic`, the ask's subject, when the ask states one. From these two fields alone, SURF builds two separate hunts.

The **exemplars** hunt seeks instances of the form itself, so stage 4 can learn the form's actual shape from several real examples rather than guess. It fires two queries — `what is a ${token}` (or `an`, by vowel-sensitive article selection) and `${token} examples full text` — the first asking what the form is, the second asking for instances of it rather than a definition. Both carry the token inside its own question, never typed alone.

The **material** hunt seeks sources about the ask's subject, when one exists, so HUNT (stage 5 — the pipeline's own admission gate for what earns a place in the ground) has something external to draw on beyond whatever was handed to the pipeline at the start. Its query is simply the topic phrase, verbatim.

When neither a form-word nor a topic is available — an anaphoric ask ("again," "the same but shorter") whose form is inherited from the conversation's own last piece, not something the open web holds — SURF declares a third, degenerate case (`hunt: "none"`) with an explicit basis message naming what was missing, rather than silently returning nothing.

Every query that does fire carries context deliberately, because a bare token does not resolve reliably: the file's own header states this as a dated, falsifiable finding, not a style preference (see Evidence, below), and there is no code path in `surfQueries` that emits the bare token.

The search-and-fetch pass is bounded on two timescales at once. Each individual network call is the caller's own timeout to keep; SURF's live implementation wraps every call in an `AbortController` tied to `WEB_FETCH_TIMEOUT_MS`, with no retry loop anywhere in the file. But a pass runs several such calls in sequence, so a slow or rate-limiting endpoint could in principle let several individually-bounded waits stack into an unbounded pass. `maxTotalMs` (defaulting to 90 seconds) closes that gap: a deadline computed once at the start of the pass is checked before every search and fetch, and once it has passed, whatever remains is marked time-bounded rather than attempted — disclosed on the record, never silently absent. The code's own comment on this bound is candid about its status: a declared starting point, not measured, easy to widen once real usage says otherwise — a ceiling chosen so a caller is never stuck indefinitely, not a claim about typical latency.

Candidates that survive the pass are selected for host diversity as a deliberate product property. Within each hunt, candidates are grouped by host and drawn round-robin, so the first N sources fetched are the most distinct N available, not the first N of one site. The returned object exposes a measured `multiple` boolean and says explicitly, in its own basis string, when fewer than two hosts were reached — "NOT multiple sources" — rather than letting a reader infer diversity from a count alone. The test suite proves this is not aspirational: one fixture returns results from three distinct hosts for a single query and asserts the fetch order is exactly host-interleaved, with a failed fetch from the third host typed as `"fetch failed"` rather than silently dropped from the count.

Failure disclosure recurs most insistently in the code's own comments, because it is the property most likely to be lost silently under refactoring. SURF distinguishes, on the record, a blocked search, an off-endpoint response, a thrown search error, a failed fetch, and a genuinely empty result set — five distinct findings a less disciplined implementation would collapse into one "no results." The basis field's own logic makes the distinction load-bearing: when no query ever reached a working endpoint, it reads "the web was not reached … a failed search, not an empty one"; only once at least one query actually completed does the basis describe candidate and fetch counts at all. The test suite pins this directly — a fully blocked pass must match `/not reached/` and must not match `/had nothing/` — the code's mechanical guarantee that this distinction cannot silently degrade into the failure mode it exists to prevent.

## Evidence

Two findings are recorded as measured, dated events rather than design assumptions, and both changed the shipped code.

The first: on 2026-09-22, before SURF's current query design was written, a bare garbled token searched alone returned noise, while the same token embedded in a natural question — "what is a whiteppr" — resolved correctly, because a real search engine's tolerance for garbled input works on context it does not have when given a single word. `CODING-LESSONS.md`'s lesson 72 documents the same finding independently: "Searched alone, 'whiteppr' returns slang noise; searched as 'what is a whiteppr', DuckDuckGo's own tolerance resolves it to the white paper." A related detail, recorded separately in lesson 71: that live run surfaced five pages titled "white paper," and the form's own name was taken from a majority of those titles — the pipeline did not hard-code what a "whiteppr" is; it asked, watched what real sources called it, and used their word.

The second is a measured regression, not a hypothetical one: putting the ask's subject into the exemplar hunt pollutes it. SURF's own comment on the exemplar queries states the case exactly — "measured live 2026-09-22 ('write a sonnet about the Cumberland River'), the subject in the exemplar query pulled six river pages into the ten, and '14 lines' fell to 4/10 — not learned." In plain terms: when the exemplar query asked about sonnets *and* the Cumberland River, six of the ten results returned were about the river rather than about sonnets, and the fraction of results correctly reporting the sonnet's fourteen-line structure dropped low enough that SHAPE's majority rule — a claim counts only when more fetched hosts state it than not — failed to learn the shape at all. The fix is structural, not a heuristic: the subject stays out of the exemplar hunt entirely and belongs to the material hunt alone, enforced directly in `surfQueries`'s code and pinned by the test suite (for "write an essay on the Cumberland River," every exemplar query must match `/essay/` and must not match `/Cumberland/`).

A related, second-order finding compounds the first: a URL both hunts independently find was originally deduplicated and kept under whichever hunt found it first — meaning pages the material hunt should have received had already been claimed by the exemplar hunt's earlier pass, and none reached the hunt as material. The fix gives a shared URL both labels rather than one, and gives each hunt its own fetch allocation so neither can spend the other's budget. Lesson 72 names why this was only found in a live run: a hand-built test fixture returns exactly what it was told to, and does not spontaneously let two different queries return overlapping URLs the way a real search index does — one interpretation, offered here, of why six earlier fixture-only test suites did not surface it.

## Conclusion

SURF's product is deliberately unopinionated about what any of its candidates mean: "This stage judges nothing. It returns candidates with provenance … Stage 4 decides whether any candidate satisfies the void's shape." That handoff is exact. SHAPE, stage 4, reads every count-and-unit claim it can find in SURF's fetched text and accepts a claim as the form's shape only when more fetched hosts state it than not — the same majority rule the exemplar-hunt-pollution finding above shows can fail when the underlying candidates are wrong. When no agreement is found, the pipeline's own stage table records the fallback explicitly: SHAPE returns control to SURF for one further, bounded round with queries that ask specifically for the form's structure, never a silent default to a hand-set number.

SURF is not a retrieval convenience bolted onto a pipeline that would otherwise work by trusting a model's prior. It is the pipeline's only mechanism for learning a form's actual shape from the world rather than assuming one, and its two measured findings — context resolves what a bare token cannot, and a subject placed in the wrong hunt actively degrades the majority signal SHAPE depends on — are the reason its query design looks the way it does. They are also exactly what a mechanical reproduction of this stage should be checked against: not merely whether it can hunt the web, but whether it keeps the ask's subject out of the exemplar hunt, carries context on every query it sends, and tells the truth about which failures were an empty web and which were a web it never reached.
