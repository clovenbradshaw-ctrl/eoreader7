# SURF: Why a Generation Pipeline Must Go Looking, and What It Found When It Did

## Thesis

A generation pipeline that trusts whatever material it was handed will confidently produce the wrong shape, so SURF — stage 3 of eoreader7's nine-stage pipeline — replaces that trust with an active, bounded, multi-source search whose two hunts, context-carrying queries, and typed failures were not designed in the abstract but corrected against a real, measured regression the day they were built.

## The problem: a pipeline that doesn't look, guesses

Ask a language model to "write a sonnet about the Cumberland River" and it will produce fourteen lines, or thirteen, or sixteen, according to whatever the model happened to internalize about sonnets during training — a shape it cannot cite, defend, or update. Ask it to write a "whiteppr" (a garbled ask this project's own testing used deliberately) and it has to guess what form is even meant before it can guess the form's shape. Either way, the pipeline is trusting the model's prior instead of checking the world, and a prior is exactly the thing that is silently wrong in the cases that matter — the unusual form, the form named by an unfamiliar or misspelled word, the ask whose subject pulls the model toward material that has nothing to do with the form it was asked to produce.

eoreader7's nine-stage generation pipeline (`pipeline-run.mjs`) treats this as a design commitment rather than a hedge. Its header lists the stages in order — PROMPT, VOID, SURF, SHAPE, HUNT, SKELETON, SK. LOOP, PATHOS, PIECE — each "proven by its own falsifier before the next was wired." Stage 3, SURF, is where the pipeline stops trusting its own priors and starts looking. Its own header states the alternative it refuses: "Not 'the file I was handed': an active search." The refusal is specific and quotes the user directive that produced it: "it surfs and seeks a shape of the void, extracting it from multiple sources … if we dont hunt for the shape of what would satisfy, everything breaks." That sentence names the actual failure mode SURF exists to prevent: not merely inaccuracy, but breakage — a downstream stage (SHAPE, stage 4) that has nothing real to learn the form's structure from, and so either fabricates one or fails silently.

A pipeline stage that only reads what it was handed also fails in a second, quieter way: it cannot tell the difference between "there was nothing to find" and "I never actually looked." Those are different findings with different consequences — the first licenses the pipeline to proceed on what it has; the second means the pipeline is about to build on an absence that was never actually confirmed. SURF's design treats this distinction as load-bearing, not cosmetic, and it shows up everywhere in the code: every failure mode the web can produce is typed on the returned object, never collapsed into a bare empty result.

## The mechanism: two hunts, both from the void's own words

SURF's central move is to derive its queries entirely from the pipeline's own prior stage — the "void" that stage 2 declared — rather than from any external configuration. `surfQueries(spec)` reads two fields off the void spec: `spec.form.token`, the form-word the ask named (its own comment gives the example "whiteppr" — a garbled word that is still what is being sought, "even when unresolved"), and `spec.topic`, the ask's subject, when the ask states one. From these two fields, and only these two, SURF builds two separate hunts:

The **exemplars** hunt seeks instances of the form itself, so stage 4 can learn the form's actual shape from several real examples rather than a guess. It fires two queries: `what is a ${token}` (or `an`, by vowel-sensitive article selection) and `${token} examples full text` — the first asking what the form is, the second asking for instances of it rather than a definition. Both queries carry the token in its own question-form context; neither is the token typed alone.

The **material** hunt seeks sources about the ask's subject, when one exists, so stage 5 (HUNT, which the pipeline's own stage table glosses as "ethos: what earns admission to the ground") has something external to ground the piece on beyond whatever was handed to the pipeline at the start. Its query is simply the topic phrase, verbatim.

When neither a form-word nor a topic is available — the code's example is an ask like "write it again," where the form is inherited from the conversation's last piece and is not something the web holds — SURF declares a third, degenerate case: `hunt: "none"`, with an explicit basis message naming what was missing (an anaphor with nothing to point at, or no form and no subject at all). This is not a silent no-op; it is a disclosed decision that nothing outside the conversation was worth seeking, which matters later when the pipeline's ledger is read back to understand why a given run surfed nothing.

Every query that does fire carries context deliberately. The file's own header is blunt about why: "Measured live 2026-09-22 before this was written: a bare garbled token ('whiteppr') searched alone returns noise; the same token WITH the ask's surrounding words resolves to what it names." This is not a stylistic preference for natural-sounding queries — it is a specific, dated, falsifiable finding about how a real search engine behaves on the actual tokens this pipeline actually receives, and the code encodes the finding as a structural rule rather than a comment: there is no code path in `surfQueries` that emits the bare token.

The search-and-fetch pass itself is bounded on two different timescales. Each individual network call — a search request or a page fetch — is the caller's own timeout to keep; `liveWeb`, SURF's live implementation, wraps every call in an `AbortController` tied to `WEB_FETCH_TIMEOUT_MS` from `organs/web.js`, with no retry loop anywhere in the file. But a pass runs several such calls one after another — `surfQueries` typically yields two or three queries, and each hunt is then entitled to its own allocation of up to `maxSources` fetches — so a slow or rate-limiting endpoint could in principle let several individually-bounded waits stack into an unbounded pass. `maxTotalMs` (defaulting to `SURF_MAX_TOTAL_MS`, 90 seconds) closes that gap: a `deadline` computed once at the start of the pass is checked before every search and every fetch, and once it has passed, remaining queries and fetches are marked `"not run: time-bounded"` or `"not fetched: time-bounded"` rather than attempted. A `withDeadline` wrapper additionally races any individual call against the pass's own remaining budget, as a safety net for an injected `search`/`fetch` that carries no timeout of its own. The code's own comment on `SURF_MAX_TOTAL_MS` is candid about its status: "a declared starting point (P9 — not measured, easy to widen once real usage says otherwise), not a promise that anything under it is fast" — a bound chosen so a caller is never stuck past a known ceiling, not a claim about typical latency.

The candidates that survive this pass are then selected for host diversity as a deliberate product property, not an incidental one. Within each hunt, candidates are grouped by host and drawn round-robin — one from each distinct host before a second from any single host — so that the first N sources fetched are "the most distinct N available, not the first N of one site." The returned object exposes `multiple: hostsFetched.length >= 2` as a measured boolean, and the human-readable `basis` string says explicitly when fewer than two hosts were reached — "NOT multiple sources" — rather than letting a reader infer diversity from a source count that might all be the same domain. The test suite proves this is not aspirational: one fixture case returns results from three hosts (`a.example`, `b.example`, `c.example`) for a single query, and asserts the fetch order is exactly host-interleaved, with the failed fetch from the third host typed as `"fetch failed"` on that source rather than silently dropped from the count.

Failure disclosure is the piece of the design that recurs most insistently in the comments, because it is the property most likely to be silently lost under refactoring. SURF distinguishes, on the record, a blocked search (401/403/429/503), an "off-endpoint" response (some other HTTP failure), a thrown search error, a failed fetch, and a genuinely empty result set — five different findings that a less disciplined implementation would collapse into one "no results." The `basis` field's own logic makes the distinction load-bearing: when no query ever reached a working endpoint, it reads "the web was not reached: … — a failed search, not an empty one"; only when at least one query actually completed does the basis describe candidate and fetch counts at all. The test suite asserts this directly — a fully blocked pass must match `/not reached/` and must not match `/had nothing/` — which is the code's way of guaranteeing, mechanically, that a distinction the header cares about cannot silently degrade into the failure mode it was written to prevent.

## What was actually measured, and what it changed

Two findings are recorded as measured, dated events rather than design assumptions, and both changed the shipped code.

The first is the context finding already quoted: on 2026-09-22, before this file was written, a bare garbled token searched alone returned noise, while the same token embedded in a natural question — "what is a whiteppr" — resolved correctly, because the search engine's own tolerance for garbled input works on context it doesn't have when given a single word. This is documented a second time, independently, in `CODING-LESSONS.md`'s lesson 72: "Searched alone, 'whiteppr' returns slang noise; searched as 'what is a whiteppr', DuckDuckGo's own tolerance resolves it to the white paper." The same lesson records that this live run surfaced five pages titled "white paper," and the form's own name was taken from a majority of those titles — the pipeline did not hard-code what a "whiteppr" is; it asked, watched what the sources called it, and used their word.

The second finding is a real, measured regression, not a hypothetical one: putting the ask's subject into the exemplar hunt pollutes it. `surf.js`'s own comment on the exemplar queries states the case exactly — "measured live 2026-09-22 ('write a sonnet about the Cumberland River'), the subject in the exemplar query pulled six river pages into the ten, and '14 lines' fell to 4/10 — not learned." In plain terms: when the exemplar query asked about sonnets *and* the Cumberland River, six of the ten results returned were about the river rather than about sonnets, and the fraction of results correctly reporting the sonnet's fourteen-line structure dropped low enough that SHAPE's majority rule (a claim counts only when more fetched hosts state it than not) failed to learn the shape at all. The fix is structural, not a heuristic: the subject stays out of the exemplar hunt entirely, and belongs to the material hunt alone. `surfQueries`'s code comment states the rule directly at the point of enforcement — "the subject stays out of the exemplar hunt" — and the test suite pins it: for the ask "write an essay on the Cumberland River," every exemplar query must match `/essay/` and must not match `/Cumberland/`, while the material query is exactly the subject phrase, verbatim.

A related, second-order finding compounds the first: a URL that both hunts independently find is deduplicated by URL and kept under whichever hunt found it first, which meant — before this was caught — that pages the material hunt should have received had already been claimed by the exemplar hunt's earlier pass, and "none reached the hunt as material," as the code comment puts it. The fix gives a shared URL both labels (`hunts: [...]`) rather than one, and gives each hunt its own fetch allocation so the exemplar pages cannot spend the material hunt's budget or vice versa. `CODING-LESSONS.md` lesson 72 names why this was only found live: "a fixture web returns what you told it to; only the real one shares URLs across queries" — six prior fixture-only test suites could not have produced this bug, because a hand-built fixture never accidentally lets two different queries return overlapping URLs the way a real search index does.

## Its place in the pipeline: SURF feeds SHAPE, never a pre-set list

SURF's product is deliberately unopinionated about what any of its candidates mean. Its own header states this as a boundary: "This stage judges nothing. It returns candidates with provenance … Stage 4 decides whether any candidate satisfies the void's shape." That handoff is exact and load-bearing. `shape.js`, stage 4, opens with the same user directive that shaped SURF's design — "we dont want a set of shapes pre-set" — and follows through structurally: there is no table anywhere mapping "sonnet" to fourteen lines. Instead, SHAPE reads every `(count, unit)` claim it can find in SURF's fetched page text ("fourteen lines," "3 quatrains," "five paragraphs"), and a claim becomes the form's accepted shape only when more fetched hosts state it than not — the same majority rule, stated once and reused, that the exemplar-hunt pollution measurement above shows can fail when the underlying candidates are wrong. If matchShape's majority rule finds no agreement, `pipeline-run.mjs`'s own stage table records the fallback explicitly: SHAPE's own arrow reads "NO → SURF again" — a second, bounded round of SURF with queries asking specifically for the form's structure, not a silent default to some hand-set number.

This is the paper's central claim made concrete: SURF is not a retrieval convenience bolted onto a generation pipeline that would otherwise work by trusting a model's prior. It is the pipeline's only mechanism for learning a form's actual shape from the world rather than assuming one, and the two measured findings above — context resolves what a bare token cannot, and a subject placed in the wrong hunt actively degrades the very majority signal SHAPE depends on — are not incidental implementation notes. They are the reason the query design looks the way it does, and they are exactly the kind of finding a mechanical reproduction of this stage should be checked against: not whether it can hunt the web, but whether it keeps the ask's subject out of the exemplar hunt, carries context on every query it sends, and tells the truth about which failures were an empty web and which were a web it never reached.
