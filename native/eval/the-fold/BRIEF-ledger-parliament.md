## The target: "the ledger" — a spreadsheet widget, grown in stages

One fold, one html artifact, MANY coupled grounds — markup grid, selection state, a formula engine, a recompute graph, styling, export. Rich enough that single edits genuinely move one ground at a time, and wrong edits visibly move the wrong one.

Stage every capability as its own sequence of SMALL asks. Never ask for two stages in one message. The staged observables (these become your harness assertions, verbatim):

1. **Birth**: "Make me a 5-column by 5-row spreadsheet grid in html, with column headers A–E and row numbers 1–5, each cell editable." Expect one fold, `plan: 1 part(s)`, ask entry, witness clean.
2. **Selection**: clicking a cell highlights it and shows its address (e.g. "B3") in a status bar. Observable: a `#status` element exists; the click handler writes the address into it.
3. **Values**: typing into a cell stores its value in a `data` object keyed by address on change/blur. Observable: the script holds a data store; setting a cell updates it.
4. **Formulas**: a cell whose text starts with `=` evaluates references, `=A1+B1` style (+ and * over cell refs and numbers is enough — refuse scope creep yourself). Observable: with A1=5, B1=7, C1 set to `=A1+B1`, C1 displays 12.
5. **Recompute**: editing A1 afterwards updates C1. Observable: change A1 to 10 → C1 displays 17.
6. **Chained dependencies**: D1 `=C1*2` follows through. Observable: with the above, D1 displays 34; then A1=1 → C1=8, D1=16.
7. **Styling pass — the mechanical rung's exercise, deliberately**: a header background color, then "change #<that color> to #<another>", then a cell-padding value change phrased "from Npx to Mpx". EXPECT these to land as `computed from your words — no model call`; if one silently goes to the model instead, that is a finding — diagnose why (check the two-literal wall, the occurrence wall, the arena) before moving on.
8. **Clear + export**: a button that clears all values; a button that serializes `data` to CSV shown in a `<pre>` (clipboard/download are sandbox-blocked — do not ask for them). Observables: clear empties the store; the CSV of the stage-6 state is exactly `5,7,12,34` in row 1 (or the equivalent for the current values).

## The method — this is the point of the exercise

- **One ground per ask.** Phrase each ask as the smallest change that would make one named observable true ("propose the smallest change so that clicking a cell writes its address into the status bar"), never "add selection support". If an ask lands but no observable moved, type that in your notes as a mass-less landing — that is data about the loop, not a success.
- **After EVERY landing, three checks**: (a) the chip — what landed, which rung (mechanical vs model), witness verdict; (b) the node harness (below) — which stage observables now pass; (c) once per stage, scrub the cursor back two positions and confirm byte-stable re-projection, then return to head.
- **The node harness — build it FIRST, before stage 1** (`eval/ledger-harness.mjs` in your worktree): pulls the fold's projection (paste bytes from localStorage via javascript_tool into a scratch file, or export ⤓), extracts script bodies with `witness.js::scriptBodies`, executes them against a stub `document` (the `preview.test.mjs`/`render.test.mjs` stub pattern — getElementById returns recorded fake elements, addEventListener captures handlers so the harness can FIRE them: `fire(cellB3,'click')`, then assert `#status` text). Each stage's observables are assertions; the harness prints a scoreboard (`stage 4: 3/3`). This is the REHEARSAL witness (the parliament's next seat) driven by hand before it is built into the app — note where it disagrees with witnessCode's clean verdicts: every such disagreement is exactly the finding the parliament exists to surface, and belongs in your report.
- **Exercise the gate on purpose, twice**: once mid-build, issue an ask designed to tempt a regression (e.g. "rename the data object to store" — a 2B will likely rename declarations but not every reference). Expect either a clean landing (fine) or a `regressed` refusal naming the findings; then confirm the NEXT ask's known-block quotes the refusal and the model steers elsewhere. Record whether it actually steered — that feedback loop's effectiveness is unmeasured and this is its first measurement.
- **The escalation ladder, by grain not size**: first failed patch → re-ask sized to the refusal's finding, not the original complaint. Second failure on the same ask → ask the STATE question ("what variable does this code need that it doesn't track? answer in one sentence, no code"), then ask for the change with the state named. Only after that, the editor as manual rescue — and say so out loud in your notes (it witnesses now, so the ground stays fresh).
- **Tally, per stage** (this is the report's spine): asks issued; landings (mechanical / patch / full / editor); refusals by kind (unlocated / ambiguous / regressed) and whether the following attempt avoided the named region; token deltas (the thinking chip shows measured in/out); wall time; harness scoreboard.
